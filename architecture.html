第 05 节

系统构成

MOS 分成四层。这一节讲每层做什么，以及最重要的一件事： 你写的应用住在最上面那一层，通过一层明确的接口跟下面打交道。

四层

应用层 · Wasm 模块

这是你写的东西住的地方。 一个应用就是一个 WebAssembly 模块，加上一份描述它的清单。

执行层 · 原生宿主 + wasm3

加载模块、提供导入函数、调用模块的导出函数。 Android 侧是 NativeActivity 加 C++，Web 侧由浏览器承担同样的角色。

接入层 · Cloudflare Worker

处理入口请求，按 UA 分流到桌面或触屏界面，再交给静态资源。

体验层 · 桌面 / 触屏界面

用户看到的界面：状态栏、Dock、桌面区、窗口。共用一套视觉样式。

一次访问走哪条路

浏览器请求 /
   ↓
Worker 读 UA → 改写成 /desktop.html 或 /mobile.html
   ↓
静态资源返回页面 → 加载 system.css → 画出桌面
   ↓
用户点图标 → 宿主加载应用的 .wasm
   ↓
wasm3 执行模块 → 结果回到界面

前两步是接入层和体验层的事，后两步才是应用真正参与的环节。 作为应用开发者，你只关心最后两行。

应用是怎么被跑起来的

宿主加载一个模块的过程是固定的，理解它有助于你组织代码：

  1. 读取应用包，取出 .wasm 文件和清单。

  2. 按清单里声明的权限，把对应的系统函数注册成模块的导入函数。

  3. 创建模块实例，分配它要用的内存。

  4. 调用模块导出的初始化函数，让它准备好自己的状态。

  5. 之后由事件驱动：有输入就调事件函数，要刷新就调绘制函数。

  6. 应用退出前调用收尾函数，让它释放资源。

应用和系统之间的接口

接口分两个方向。下面这组名字是约定，写应用时照着来：

宿主调用应用（你要导出）

导出函数 什么时候被调用 要做什么
mos_init 模块加载完成后，一次 初始化状态，准备好要用的内存
mos_event 用户输入、生命周期变化 处理事件，更新内部状态
mos_frame 每次需要刷新界面 把该画的东西画出来
mos_stop 应用退出前，一次 释放资源，保存该存的

应用调用系统（你要导入）

导入函数 用途 需要的权限
mos_log(ptr, len) 输出一行日志，调试用 无需声明
mos_now_ms() 当前时间戳，毫秒 无需声明
mos_read_asset(id, buf, len) 读取自己包内的资源文件 无需声明
mos_store_get / mos_store_set 读写应用自己的持久化数据 storage
mos_notify(title, body) 往状态栏发一条通知 notify
权限是清单里写死的

用到 storage 或 notify 这类受控能力， 必须在清单的 permissions 里声明，安装时会列给用户确认。 没声明的话，宿主根本不会把这些函数注册进来，模块加载时就找不到导入。

四个仓库

仓库 内容 跟你有关吗
MOS Web 入口、桌面与触屏界面 改入口或界面时才需要
mos-android 原生宿主、wasm3、C++ 主循环 要加新的导入函数时才需要
mos-repo 软件源，放应用包 发布应用时要用
mos-doc 这份文档 发现写错时欢迎改

四个仓库之间没有代码依赖，谁也不 import 谁，只是职责上分层。

这一节要点

  • 四层：应用、执行、接入、体验，你写的东西在最上面
  • 加载流程固定：读包 → 注册导入 → 建实例 → 调 init → 事件驱动 → 调 stop
  • 导出 mos_init / mos_event / mos_frame / mos_stop 给宿主调
  • 受控能力要在清单 permissions 里声明，否则宿主不会注册
