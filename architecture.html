第 03 节

系统架构

MOS 分成四层。上面两层跑在 Web 侧，一次 HTTP 请求就走完了； 下面两层跑在 Android 侧，跟网络没有关系。这一节讲清楚每层做什么， 以及一个关键事实：这两半目前各跑各的，中间没有连起来。

四层分别是干什么的

体验层 · desktop.html / mobile.html

用户看到的东西。桌面端有状态栏、Dock、欢迎页，深蓝主色； 触屏端是另一套布局。两边共用 public/assets/system.css。

接入层 · Cloudflare Worker

只有 src/index.js 一个文件。收到请求后判断设备类型，改写到对应页面，再交给静态资源。

执行层 · NativeActivity + C++

Android 侧的宿主。主循环在 main.cpp，调度在 engine.cpp， Wasm 的加载调用在 wasm_runner.cpp。

应用层 · wasm3 + Wasm 模块

应用逻辑编译成 .wasm，交给 wasm3 执行。目前只有一个 sample.wasm 示例。

一次访问是怎么走的

这是整个 Web 侧的完整链路，没有别的东西了：

浏览器 GET /
   ↓
Worker (src/index.js) 读 UA
   ↓
判定触屏 → pathname = /mobile.html
判定桌面 → pathname = /desktop.html
   ↓
env.ASSETS.fetch() 取静态文件
   ↓
返回 HTML → 浏览器加载 system.css → 画出桌面

对应的代码就这几行，全部的服务端逻辑：

if (url.pathname === '/') {
  const isTouchDevice = /android|iphone|ipad|mobile/i.test(userAgent);
  url.pathname = isTouchDevice ? '/mobile.html' : '/desktop.html';
}
return env.ASSETS.fetch(new Request(url, request));

注意最后一行：改完路径转手给静态资源，Worker 自己不产出内容。 所以这一层没有后端、没有数据库，改界面就是改 public 下的 HTML 和 CSS。

Android 侧是怎么启动的

流程和 Web 侧完全不同，两者之间没有任何通信：

系统启动 Activity (NativeActivity)
   ↓
native_app_glue 建立事件队列，拉起 C++ 主循环
   ↓
main.cpp 循环取事件 → 交给 engine.cpp 分发
   ↓
需要跑应用时 wasm_runner.cpp 加载 sample.wasm
   ↓
wasm3 逐条解释执行 → 结果回到 C++

三个 cpp 文件通过 app/src/main/cpp/CMakeLists.txt 编成一个 native library， 再放进 jniLibs 打进 APK。

现在缺的那一段

这是理解现状最重要的一点

Wasm 模块目前拿不到任何系统能力。它没有文件、没有网络、拿不到时间，只能自己算自己的。 原因在 02 节讲过：Wasm 跑在沙箱里，要用外部能力得由宿主导入函数，而这套导入约定还没写。

所以严格来说，现在还没有真正的「应用」，只有一个能跑起来的 Wasm 示例。 后面所有关于应用的设想，都卡在这一步。

另外几处还没接上的地方：

  • Web 端和 Android 端各写一套界面，视觉靠人工对齐，没有共享的部分
  • 桌面上的图标点开没有实际内容，Dock 目前是静态的
  • 应用从哪来、怎么装、版本怎么管都还没开始设计
  • Native 层有日志和崩溃处理，Web 侧什么都没有

这一节要点

  • 四层：体验、接入、执行、应用，前两层在 Web，后两层在 Android
  • Web 侧一次请求走完，Worker 只做 UA 分流，最终由静态资源产出页面
  • Android 侧由 NativeActivity 拉起 C++ 主循环，wasm3 负责执行模块
  • 两半之间没有通信，Wasm 拿不到系统能力是当前最大的缺口
