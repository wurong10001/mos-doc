第 02 节

预备概念

MOS 把几样平时不太会放在一起的东西拼到了一起。这一节把它们逐个讲清楚， 后面看架构和代码就不用边看边查了。已经熟悉的可以直接跳到 03。

WebAssembly

一种字节码格式。你用 C、C++、Rust 写的代码，编译成 .wasm 文件， 运行时拿来加载执行。它不是给人读的，是给虚拟机读的，所以体积小、解析快。

关键点在沙箱：Wasm 模块默认什么都碰不到，不能直接读文件、不能开网络。 它想用外部能力，必须由宿主显式地把函数「导入」给它。这条限制决定了 MOS 里应用和系统的边界怎么划，后面会反复提到。

wasm3

一个 Wasm 解释器。解释器的意思是逐条读指令、逐条执行，不做编译优化。 常见的另一类实现是带 JIT 的（比如 Wasmtime、V8 里的 Wasm），先把字节码编译成本地机器码再跑，快很多，但体积也大得多。

MOS 选 wasm3 的理由很实际：它只有几个 C 文件，塞进 APK 不占地方，在手机上也能跑。 代价是执行速度慢一截。对一个还在验证结构的原型来说，这个交换是划算的。

Cloudflare Worker

一段跑在 Cloudflare 边缘节点上的 JavaScript。没有服务器，没有进程要维护， 请求来了就执行这段代码，执行完就结束。代码里能拿到 request，要返回一个 Response。

MOS 用它做的事很轻：读一下 UA，改一下路径，把请求转给静态资源。 这类「挡在静态文件前面做点小处理」的活，正是 Worker 最擅长的场景。

NativeActivity

Android 提供的一种入口，让整个应用可以不写 Java UI，直接由 C++ 接管。 系统把事件（触摸、生命周期、窗口变化）通过 native_app_glue 这个胶水层喂给你的 C++ 主循环， 你自己处理，自己绘制。

好处是所有逻辑在一套 C++ 代码里，跟 Wasm 那层打交道的成本很低。 代价是界面相关的东西都得自己来，没有现成的 View、RecyclerView 可用。

NDK、CMake、jniLibs

这三个经常一起出现，容易混：

NDK

工具集。提供编译 Android 原生代码所需的编译器和头文件。

CMake

构建工具。通过 CMakeLists.txt 描述「哪些源文件编成哪个库」，Gradle 会调用它。

jniLibs

一个目录位置（app/src/main/jniLibs）。放进去的 .so 会被直接打进 APK， 不需要本地再编译一次。

这个区别在 MOS 里很重要

mos-android 的原生库是预编译好放进 jniLibs 的，不走 NDK 现场编译。 所以你改了 C++ 源码之后，光跑 ./gradlew assembleDebug 不会生效， 必须先重新编译出 .so 再拷进去。05 节会细说。

静态站点与 GitHub Pages

这个教程本身就是静态站点：六个 HTML 文件加一个 CSS，没有后端。 推到仓库的 main 分支，GitHub Pages 会自动把它发布到一个公开地址，改完推上去过一会儿就能看到。

这一节要点

  • Wasm 默认跑在沙箱里，要用外部能力必须靠宿主导入函数
  • wasm3 是解释器，小而慢；带 JIT 的运行时大而快
  • Worker 是请求进来才执行的轻量 JS，适合做分流和改写
  • NativeActivity 让 C++ 直接接管 Android 应用，代价是没有现成 UI 组件
  • jniLibs 里放的是预编译好的 .so，改 C++ 后必须重新编译
