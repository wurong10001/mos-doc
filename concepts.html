第 04 节

预备概念

MOS 的应用跑在 WebAssembly 里，由原生宿主加载执行。 这一节把相关的几个概念讲清楚，后面写应用时不用边写边查。

WebAssembly

一种字节码格式。你用 C、C++、Rust 写的代码，编译成 .wasm 文件， 由运行时加载执行。它不是给人读的，是给虚拟机读的，所以体积小、解析快， 而且同一个文件在不同 CPU 架构上都能跑。

对 MOS 来说这点很关键：应用编译一次，桌面上能跑，手机上也能跑，不用为每种设备单独出包。

沙箱、导入与导出

这是整个开发模型里最重要的一条：Wasm 模块默认什么都碰不到。 它不能直接读文件、不能开网络、不知道现在几点。

模块和外界打交道只有两个方向：

导入（import）

模块声明「我需要一个叫 X 的函数」，由宿主在加载时把真实实现填进去。 模块想用系统能力，走的都是这条路。

导出（export）

模块把自己的函数暴露出去，让宿主调用。 宿主靠这些导出函数通知应用「该初始化了」「有一帧要画」「用户点了一下」。

记住这个模型

应用是被动的。它不会自己去拿东西，只能等宿主调用它的导出函数， 再在过程中通过导入函数请求系统能力。写应用时脑子里要有这个主客关系。

wasm3

MOS 用的 Wasm 运行时。它是解释器：逐条读指令、逐条执行，不做编译优化。

另一类实现带 JIT（即时编译），先把字节码编译成本地机器码再跑，快很多， 但体积和内存占用也大得多。wasm3 只有几个 C 文件，塞进手机应用包里很轻， 代价是执行速度慢一截。

对你的实际影响：写应用时别指望它有本地代码的性能， 适合逻辑型、交互型的应用，不适合在模块里跑重计算。

Cloudflare Worker

一段跑在边缘节点上的 JavaScript。没有服务器要维护，请求来了执行，执行完就结束。 能拿到 request，返回一个 Response。

MOS 用它做接入：读 UA 判断设备，把请求改写到对应页面，再交给静态资源。 这一层你作为应用开发者基本不用碰，除非你要改入口行为。

NativeActivity

Android 提供的一种入口，让整个应用可以不写 Java UI，直接由 C++ 接管。 系统把触摸、生命周期、窗口变化这些事件通过 native_app_glue 喂给 C++ 主循环，由宿主自己处理和绘制。

好处是所有逻辑在一套 C++ 代码里，跟 Wasm 那层打交道的成本很低； 代价是界面相关的东西都得自己来，没有现成的 UI 组件可用。

NDK、CMake、jniLibs

这三个经常一起出现，容易混：

NDK

工具集。提供编译 Android 原生代码所需的编译器和头文件。

CMake

构建工具。用 CMakeLists.txt 描述「哪些源文件编成哪个库」，Gradle 会调用它。

jniLibs

目录位置（app/src/main/jniLibs）。 放进去的 .so 会被直接打进 APK，不需要本地再编一遍。

静态站点与 GitHub Pages

这份文档本身就是静态站点：几个 HTML 加一个 CSS，没有后端。 推到仓库的 main 分支，GitHub Pages 会自动发布到公开地址。

这一节要点

  • Wasm 编译一次到处能跑，这是 MOS 选它做应用格式的原因
  • 模块默认在沙箱里：用系统能力靠 import，被调用靠 export
  • 应用是被动的，等宿主调用，不要写主动去拿东西的代码
  • wasm3 是解释器，小而轻，不适合重计算
  • Worker 只管接入分流，NativeActivity 让 C++ 接管 Android 界面
