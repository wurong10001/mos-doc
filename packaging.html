打包与发布

模块编出来只是第一步。要让用户能在 MOS 上装到它， 需要把模块和资源按约定的结构收成一个应用包，写一份清单，再提交到软件源。

目录结构

一个应用包的源码目录长这样：

my-app/
├── app.toml          # 清单，必需
├── icon.png          # 图标，必需
├── src/              # 源码
│   └── main.c
├── assets/           # 应用自带的资源
│   └── data.bin
└── dist/
    └── app.wasm      # 编译产物，打包时打进去

dist/ 里的是编译产物，不进版本库； 发布时打的是它，不是源码。

清单 app.toml

清单描述这个应用是什么、需要什么。一个例子：

id = "dev.example.clock"
name = "时钟"
version = "0.1.0"
entry = "dist/app.wasm"
icon = "icon.png"

description = "一个显示当前时间的示例应用"
author = "your-name"

permissions = ["storage"]

[resources]
limit_memory_kb = 1024

必填字段

字段 说明
id 唯一标识，反域名写法。一旦发布就不要改，改了等于换了个应用
name 显示名，出现在桌面图标下方和窗口标题栏
version 三段式版本号，见下面的版本规则
entry Wasm 模块在包内的路径
icon 图标文件路径，建议正方形 PNG

选填字段

字段 说明
description 一句话说明，安装时显示给用户
author 作者名或联系方式
permissions 要用到的受控能力，见 05 节的接口表
[resources] 资源上限，比如内存配额
permissions 别多写

用到什么声明什么。多声明的能力在安装时会列给用户， 平白增加顾虑；而且以后要收回权限，等于改了应用的契约。

版本规则

用三段式 主版本.次版本.修订号，递增规则如下：

  • 修订号 — 修 bug，行为不变，用户无感
  • 次版本 — 加了功能，向下兼容，老数据还能用
  • 主版本 — 有不兼容的改动，比如改了数据格式、去掉了功能

0.x.x 阶段可以宽松些，但一旦有别人在用，就按上面的来。 已经发布过的版本号不能重新发 —— 改了内容就往上升。

打包

应用包就是一个归档文件，扩展名 .mosapp。 里面是清单、图标、Wasm 模块和资源，目录结构跟源码目录保持一致： 

$ mosapp pack ./my-app
  → my-app-0.1.0.mosapp

$ mosapp check my-app-0.1.0.mosapp
  清单字段完整 ✓
  entry 指向的模块存在 ✓
  声明的权限均已实现 ✓

发布前先 check 一遍。它会验证清单字段是否齐全、 entry 指向的文件在不在、声明的权限宿主是否支持 —— 这几项出错的话，用户那边会装到一半失败。

提交到软件源

软件源就是 mos-repo 仓库，走 Pull Request 的流程：

  1. Fork mos-repo，在 apps/<你的 id>/ 下建目录。

  2. 把应用包和清单放进去，.wasm 要一起提交，源仓库需要能直接拿到产物。

  3. 更新仓库里的索引文件，把新应用 id 和版本登记上去。

  4. 发 Pull Request，说明这个应用做什么、为什么需要它声明的权限。

  5. 合并后，用户在 MOS 的软件源里就能搜到并安装了。

为什么要走 PR

软件源是集中式的，装什么由这个仓库决定。 走 PR 是为了让每个进来的应用包都经过一次人工过目 —— 看它声明了哪些权限、包里到底有什么。这是这套设计换来可控性的代价。

发布之后

  • 改了代码就升版本号，重新打包，再发一个 PR 更新包文件
  • 用户那边看到新版本可以更新，也可以留在旧版本
  • 发现问题需要下架，在 PR 里说明原因，从索引里移除

这一节要点

  • 包结构：app.toml + icon.png + dist/app.wasm + 资源
  • 必填字段 id / name / version / entry / icon，id 发布后不能改
  • 版本三段式，已发布的版本号不能重发
  • 发布前 mosapp check，提交到 mos-repo 走 PR
